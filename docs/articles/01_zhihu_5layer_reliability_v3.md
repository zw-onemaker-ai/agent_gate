# 我跑了100多次多Agent管线，发现每次翻车的原因都差不多

事情的起因是这样的。

我一个人要交付完整的软件产品——从需求分析到上线验证，大概十二个环节。一个人不可能同时是产品经理、设计师、后端、前端、测试、安全工程师。但我可以让 AI 分别扮演这些角色，串成一条管线：

```
创意 → 需求分析 → 产品设计 → 视觉 → 后端 → 前端 → 测试+安全 → 运维 → AI集成 → 审查 → 验收
```

一开始我想得很简单：写好提示词，把它们串起来，完事。

跑了几次之后发现——完全不是。

说真的，前几次翻车我还以为是偶然。跑到第 20 次、第 50 次、第 100 次之后，我发现翻车的模式高度重复。不是什么深奥的 AI 对齐问题，就是一些特别朴素的、工程层面的坑。而且不管你用 Claude 还是 Qwen，该翻还是翻。

我把这些坑归成了 5 类。

---

## 1. Agent 是金鱼

每次对话结束，Agent 的状态就清零了。

想象一下：管线走到第 8 步崩了。前面 7 个 Agent 的产出——需求文档、产品规格、设计稿、后端代码、前端页面——全在上下文窗口里，窗口一爆，全没了。

你从头再来一遍。但这次 Agent 生成的代码跟上次不一样。接口签名变了。后面几步基于旧接口写的代码全废了。

搞了半天发现不是 Agent 的问题，是没做记忆持久化。Agent 本来就是无状态的——调完就消失。你得在 Agent 外面搞一层记忆：项目文件存磁盘，会话日志记进度，断点能恢复。这个道理特别简单，但我前 20 次都没认真做，每次翻车了才后悔。

---

## 2. 传话游戏

你玩过传话游戏吧？第一个人说「今天天气真好」，传到最后一个人变成「今天有雷暴」。

Agent 管线里更严重。

上游 Agent 产出一份 15KB 的产品规格文档。下游需要从中提取 API 接口定义来写前端。你把 15KB 全塞给它——注意力稀释，读到后面忘了前面。你只给它摘要——关键细节丢了。

还有一个更恶心的情况。上游 Agent 把接口从 `/api/users` 改成了 `/api/v2/users`，但没通知下游。下游还在调老接口，调不通，反复重试。等发现的时候管线已经转了三轮，Token 烧了一堆。

说白了就是 Agent 之间没有共享大脑。上游改了东西，下游完全不知道。后来我搞了一套机制：上游产出必须物化为不可变的快照，下游先读 200 字的摘要再决定要不要深读源文件。同时监控上下文总大小——有些模型有效窗口就 8K，不能无脑全塞。

---

## 3. 说做了，但没做

这是最常见的，也是破坏力最大的。

Agent 说「我已经写好了 main.py，FastAPI 应用就绪，包含 /health 端点」。下游基于这个承诺继续干活——写前端页面、写测试用例、写部署配置。三步之后你发现：main.py 根本不存在。三步全白干了。

我们用最土的办法堵这个洞：每个 Agent 产出后，Bash 检查文件是不是真的存在、是不是空的、语法对不对。

但接着发现了更阴险的问题——Agent 可以伪造验证结果。

它可以说「我运行了 pytest，28 个测试全部通过」。你怎么知道它真的跑了？我们就加了一条硬规矩：所有验证命令必须以 `echo "EXIT:$?"` 结尾。Agent 可以编测试结果，编不了 Bash 退出码。你说「把 EXIT_CODE 贴出来」——有就是有，没有就是编的。

这还不算完。Agent 还会声称「覆盖了所有验收标准」。我们又加了交叉验证——下游 Agent 随机抽查上游的覆盖声明，实际去执行。你说 API 可达？我 curl 一下。你说页面五态完整？我一个一个状态测。

---

## 4. 换了模型，不换提示词

Claude 和 Qwen 对同一个提示词的响应，差得不是一点半点。

当你的管线需要混用多种模型的时候——敏感数据的 Agent 用本地 Ollama，代码生成的用百炼，复杂推理的用 Claude——你不能给所有 Agent 同一套提示词。Claude 能理解的长指令，Qwen 可能需要拆成两步。DeepSeek 对中文的理解方式跟 OpenAI 完全不同。

更麻烦的是，Agent 失败不一定是能力问题。有时候就是提示词没写好。换个写法可能就过了。

我后来做了一个自动评分的东西：Agent 产出过闸门失败了 → 自动给这次用的提示词打分 → 低于 80 分自动重写 → 下一轮用新提示词重试。很多时候就过了。不是模型不行，是提示词没配好。

---

## 5. 静默卡死

12 步管线，任何一步卡住，整条线就死了。

而且往往是静默的。不报错、不超时、不崩溃——就是不动了。你过了三小时回来看，发现卡在第 7 步。

常见的情况：Agent 返回了空内容，管线不知道该怎么处理；闸门连续 3 次失败，直接放弃了；并行阶段某个 Agent 挂了，但其他 Agent 还在等它；错误不知道归类到哪个 Agent，管线不知道该回环给谁。

我在管线里加了一个诊断模块——卡在哪一步、什么原因、以前出现过没、建议怎么修。同时留了一个人工入口：错误实在没法自动分类的时候，结构化提问给人，不给空白输入框。人不需要盯着管线，只在被叫的时候看一眼。

---

## 问题不在模型，在系统

说一个可能反常识的结论：**强模型和弱模型在这 5 类错误上的表现差异很小。**

Claude 和 Qwen 都会声称文件存在但实际不存在。都会在上下文稀释后胡编。都会静默卡死。

这不是「模型不够强」的问题。这是「没有验证机制」的问题。

市面上所有主流多 Agent 框架——LangChain、CrewAI、AutoGen、Dify、LangGraph——都在解决「怎么把 Agent 串起来」。它们的默认假设是：Agent 的产出是可信的。这个假设在面对以上 5 类问题时，一点防御力都没有。

---

## 我把这些沉淀成了 5 层东西

基于这些教训，我把解决方案做成了一套完整的架构，在 GitHub 上开源了：[AgentGate](https://github.com/zw-onemaker-ai/agent_gate)。

5 层，每层解决一类问题：

- **记忆层**：Agent 不会消失了。项目记忆存磁盘，会话日志记进度，断点能恢复。
- **上下文层**：Agent 之间传递信息不再靠运气。上游产出物化快照，下游按需读取，总量有预算控制。
- **防幻觉层**：Agent 说的话要验证。文件存在检查、EXIT 指纹、交叉验证——三道闸门，一道都绕不过去。
- **提示词层**：换了模型自动适配提示词。产出不达标自动评分、自动重写、重新来过。
- **流程层**：管线自己能给自己看病。卡住了有诊断，修不了知道叫人。

单层不够。就像汽车安全——刹车、安全带、气囊，单用哪个都不够，全配上才敢上路。

---

## 一个我觉得比较重要的设计

AgentGate 里面有个刻意的不对称：**设计脑是 LLM，执行脑不是。**

设计脑分析需求、拆解任务、分配 Agent——需要创造力，可以用 LLM。

执行脑调度 Agent、过闸门、判定回环——需要可靠性，**一行 LLM 都不调。** 就是纯 Python 规则引擎。每一次 PASS/FAIL、回环到谁、重试几次，全是硬编码的，可以追查，可以复现。

为什么？因为如果执行脑也是 LLM，它自己就会幻觉。CrewAI 的 Manager Agent 就是一个 LLM 在做调度——它可能做出错误的调度决策，而且没人在验证 Manager 自己的决策。我把「不信任」贯彻到底：连主脑自己也被闸门约束。

---

## 真实踩过的几个坑

不是理论推演，是反反复复出现、排查了很久才定位的：

有一个项目，界面样式改了三次没变化。怎么调都不生效。搞了两天才发现——两个 CSS 文件里写了同名的选择器，后面的那个静默覆盖了前面的。Agent 改了第一个文件，以为改了，其实被覆盖了。

还有一次，数据库里的表全「没了」。查了半天发现是 Agent 用相对路径 `./data/db.sqlite` 连接数据库。工作目录一变，连到了另一个空库。Agent 基于空库继续生成代码，Schema 全错了。

有一次 Agent 跟我说「main.py 已经写好并且测试通过了」。我说好，继续。下游三个 Agent 基于这个信息工作了。最后发现——文件从来没存在过。这就是后来加 EXIT_CODE 指纹的直接原因。

还有缓存。你改了 CSS，刷新浏览器，没变化——浏览器用的是旧缓存。不是 Agent 的问题，但用户看到的就是「没改」。

---

这些就是我跑了一百多次多 Agent 管线之后，觉得最值得说的东西。不是什么高深的理论，就是一些特别朴素的工程问题——记忆、传话、验证、适配、诊断。每个单独看起来都不难解决，但合在一起，缺一个就可能全线翻车。
